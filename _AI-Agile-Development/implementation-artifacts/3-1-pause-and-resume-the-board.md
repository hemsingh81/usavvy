## Story

As a learner,
I want to pause and resume the lesson board at any moment,
so that I can step away without losing my place.

## Acceptance Criteria

1. **Given** a Beat is actively narrating and rendering on the board **When** I select Pause **Then** narration audio and board animation halt immediately at the current word/element position within the current Beat **And** the paused state (Beat id, narration offset, board render state) is persisted to the session
2. **Given** the board is paused **When** I select Resume **Then** narration resumes from the exact paused offset and board rendering continues from where it stopped, without replaying or skipping content
3. **Given** I paused a session and closed the app, or the session sat idle overnight **When** I reopen the same lesson on the same or a different day or device **Then** the board restores to the exact paused Beat and offset, in the paused state, ready for Resume
4. **Given** the narration audio stream cannot be reestablished when I select Resume (e.g., VoicePort error) **When** the failure occurs **Then** the system shows a retry affordance without losing the saved position, and the board visual (text/diagram/etc.) remains at the paused state
5. **Given** a LearningSession reaches its last Beat, or the learner explicitly ends the session **When** that occurs **Then** a `learning_session.ended` domain event is published per AD-13, giving Epic 1's Activity History (Story 1.11) and NFR-26's "checkable later" requirement a defined completion signal — added per architecture AD-18

## Review Findings

Three parallel adversarial reviews (Blind Hunter, Edge Case Hunter, Acceptance Auditor) ran against the diff. Blind Hunter and Edge Case Hunter independently converged on the same two core session-lifecycle gaps, which is strong corroboration. All genuine findings were patched and covered by new tests; nothing was disputed. Deferred items logged in `deferred-work.md` ("Deferred from: code review of story-3-1").

### Patched

- **HIGH — no DB-level enforcement of the idempotent-session claim; race produces duplicate active sessions.** `createOrResumeLearningSession`'s "check then insert" had no unique constraint, advisory lock, or transaction wrapping the decision — two concurrent calls for the same `(userId, conceptId)` (double-click, retried request, two tabs) could both miss the initial SELECT and both insert, and the SELECT itself had no `ORDER BY`, making which duplicate got returned on later calls non-deterministic. Fixed with a partial unique index (`learning_sessions_user_concept_active_idx` on `(user_id, concept_id) WHERE status <> 'ended'`, migration `0001_aromatic_pandemic.sql`) plus an ordered/status-filtered lookup and a unique-violation fallback in `service.ts`, mirroring `services/ingestion`'s `confirmOutline()` precedent for the identical race shape. Covered by a new concurrency test (`Promise.all` of two concurrent creates converges on one DB row) and a new "ignores a prior ended session, returns the new one" ordering test.
- **HIGH — `pauseLearningSession` had no status guard, allowing an ended session to be resurrected.** Pausing an already-`"ended"` session silently flipped it back to `"paused"` while `endedAt` stayed set (an internally inconsistent record), after which Resume could reactivate it — undoing a session the state machine intended to be terminal. Fixed: rejects up front with `VALIDATION_ERROR`, and the write itself is additionally scoped to `status <> "ended"` so a concurrent `end` landing between the check and the write can't be raced past either. Covered by a new test asserting the DB row is untouched after the rejected call.
- **MEDIUM — `recordBeatReached` had the identical missing-guard gap.** A stray/late call on an already-ended session could silently move `currentBeatId` on a record meant to be immutable, and (if the reached Beat happened to be the last one) re-trigger the end path a second time. Fixed with the same guard-plus-scoped-write pattern as the pause fix above. Covered by a new test asserting `currentBeatId` is unchanged.
- **MEDIUM — lost-update in `resumeLearningSession`: a concurrent `end` could be silently reversed.** The final "flip to active" write was unconditional on status; if a concurrent `end`/auto-end landed while the (awaited) VoicePort call was in flight, the blind write afterward reactivated the now-ended session, contradicting the already-published `learning_session.ended` event. Fixed by re-checking `status = "paused"` at write time; on a lost race the caller now gets a distinguishable `SESSION_STATE_CHANGED`/409 instead of silently winning. Covered by a new test that deterministically injects the "concurrent" end from inside the mock VoicePort call (JS's single-threaded event loop makes this reproducible without real parallel connections) and asserts the DB is left `"ended"`, not reversed.
- **Proactive, same-root-cause fix (not separately flagged by a reviewer): `endLearningSessionInternal`'s own write had the same unscoped-write shape** — two genuinely concurrent `end` calls (an explicit end racing `recordBeatReached`'s auto-end branch) could both pass its no-op check and both write/publish, double-publishing `learning_session.ended`. Scoped the write to `status <> "ended"` the same way, with the loser treated as the idempotent no-op it actually is (re-reads and returns the winner's row) rather than erroring.
- **Task-compliance gap — Task 4's "minimal live integration proof" was checked off but didn't exist.** What existed only exercised the service module directly (bypassing HTTP) or mocked the forwarding function. Added `services/board-orchestration/tests/modules/learningSessions/routes.test.ts`: a real `app.inject()`-based test exercising the full create → pause → resume → beat-reached → end lifecycle through the real Fastify routes, real auth/trust-boundary checks, and the real database — deliberately not spanning an actual live `gateway` process (see `deferred-work.md` for why that's a documented scope choice, not a gap).
