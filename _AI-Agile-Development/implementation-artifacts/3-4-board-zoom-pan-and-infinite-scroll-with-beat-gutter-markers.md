# Story 3.4: Board Zoom, Pan, and Infinite Scroll with Beat Gutter Markers

Status: done

*(Epic 3, FR-B-31. Unlike Stories 3.1-3.3, this story is 100% frontend — no `board-orchestration` change, no new endpoint. Per explicit user decision (2026-08-06, asked directly rather than assumed): build the real infinite-scroll/zoom/pan canvas directly into the already-signed-off mock `BoardPage.tsx`, with no separate mock-first sign-off pass for this specific change — the user chose "just build it directly now" over re-running the mock-first-epic-kickoff convention for this UX shift. Read the CRITICAL SCOPE NOTE before starting any task.)*

## Story

As a learner,
I want to zoom, pan, and scroll through the board with visible Beat markers,
so that I can navigate a long lesson visually and orient myself.

## Acceptance Criteria

1. **Given** the board contains one or more rendered Beats **When** I use zoom controls or pinch/scroll-wheel gestures **Then** board content scales smoothly between a minimum and maximum zoom level without loss of legibility or layout breakage
2. **Given** board content exceeds the viewport **When** I drag/pan or scroll vertically **Then** the board pans/scrolls on an infinite vertical canvas, loading additional rendered Beat content as needed without blocking interaction
3. **Given** multiple Beats have been rendered in the session **When** I view the board's gutter **Then** a marker for each Beat is shown, positioned to reflect that Beat's location on the board, and each marker is clickable to jump the viewport to that Beat
4. **Given** I click a Beat marker in the gutter **When** the jump completes **Then** the viewport centers on that Beat's rendered content at a readable zoom level

- **This story restructures `BoardPage.tsx`'s canvas from "one Beat visible at a time, swapped on navigation" to a genuine stacked, scrollable, zoomable vertical canvas — a real change to the already-signed-off mock's interaction model, done directly per explicit user instruction, not gated behind a fresh mock/sign-off pass.** Today's canvas renders exactly one Beat's content (`displayedBeat = overlayBeat ?? lessonBeat`) and Forward/Back *swap* it. `DESIGN.md`'s own Layout & Spacing section already describes the intended model: *"The Board canvas itself... is an infinite vertical scroll (FR-B-31)... each Beat claims the vertical space its content actually needs."* This story makes the mock actually behave that way for the FIRST time.

Nothing here is "more real" than before — it's a UX/interaction upgrade to the same mock.
- **Rendering model: render `concept.beats.slice(0, lessonBeatIndex + 1)` as a stacked column, not just the active Beat.** Every Beat *before* the active index (`index < lessonBeatIndex`) renders fully revealed unconditionally (it's "behind you" in the stack — once passed, it stays complete, regardless of whether it's in `visitedBeatIds`, which continues to exist unchanged for the Progress Disclosure count only). Only the Beat *at* `lessonBeatIndex` keeps today's progressive-reveal behavior (`revealedUnits`/the tick timer). The bookmark control, the "Source:" tag, and the "you've reached the end" block stay attached **only** to the active Beat's section, exactly where they render today — do not duplicate them onto every stacked Beat (this is also what keeps the existing `BoardPage.test.tsx` bookmark test passing unmodified: it queries `getByRole("button", { name: "Bookmark this Beat" })` and would break on a duplicate match).
- **The "explain more" detour (`overlayBeat`) is NOT part of the stack.** When `overlayBeat` is set, it still fully replaces what's shown in the canvas (exactly like today — `displayedBeat = overlayBeat ?? lessonBeat`, only `displayedBeat`'s content renders when there's an overlay) — the lesson stack is hidden underneath, not stacked alongside the detour. This preserves every existing overlay-related test (`'Explain more' -> ...`, `'Ask anything' ...`) unmodified.
- **Zoom is a CSS `transform: scale(...)` on the stacked-content wrapper, clamped to a fixed min/max (e.g. `0.5`–`2.0`), controlled by `+`/`-` buttons plus a `Ctrl`+wheel handler** (not plain wheel — plain wheel/scroll must stay reserved for vertical scrolling per AC #2, so zoom needs a distinct trigger; `Ctrl`+wheel is the same convention browsers themselves use for page zoom). No pinch-gesture implementation is required or expected to be meaningfully testable in `jsdom` — implement it if trivial via the same wheel/pointer handlers, but do not build bespoke multi-touch gesture-recognition code from scratch for this story; the buttons and `Ctrl`+wheel path alone satisfy AC #1's "zoom controls or... gestures" (an "or").
- **Pan is native scrolling, not a bespoke drag-physics engine.** The stacked-content container becomes a scrollable box (`overflow-y: auto` for the vertical "infinite scroll" the AC and `DESIGN.md` describe; `overflow-x: auto` so zoomed-in content wider than the viewport can be panned horizontally too). Touch-drag-to-scroll is a native browser behavior on a scrollable container — no custom pointer-drag/translate code is needed or expected. Do not build a custom 2D pan implementation; it would be over-engineering relative to what the ACs actually require.
- **AC #2's "loading additional rendered Beat content as needed" has no real trigger condition today, honestly.** Every Beat in a mock session is already in `MOCK_CONCEPT.beats` from the start — there is no async/paginated source to load from (the same boundary Story 3.3 already hit and deferred for the *real* backend: no `GenerationPort` binding exists to generate a Beat on demand). This story satisfies the AC's actual operative requirement — scrolling/panning never blocks interaction, because there is nothing to await — without fabricating a fake loading spinner for content that isn't actually loading. Note this honestly in Dev Notes; do not invent a simulated-network-delay Beat-loading mechanism that doesn't correspond to anything real.
- **Gutter markers: reposition based on each Beat section's *measured* position in the scrollable canvas (via `ref`s + each section's `offsetTop`/the canvas's `scrollHeight`), not a naive index-based percentage.** This is what actually satisfies AC #3's "positioned to reflect that Beat's location on the board" — Beats have different content lengths (a one-paragraph Beat vs. a Beat with a table+text), so their real vertical position is not evenly spaced. **Known, accepted test limitation: `jsdom` does not compute real layout** (`offsetTop`/`scrollHeight` are always `0` in `jsdom`), so this logic cannot be pixel-verified by the existing test suite — write it for real (it will work correctly in a real browser), and test only the parts that are actually testable in `jsdom` (that markers render, in the right count, clickable, and that clicking one triggers the expected jump behavior/state — see Task 3).
- **Clicking a gutter marker: jump to that Beat (`goToLessonBeat`, unchanged existing function) AND additionally scroll that Beat's section into view (`scrollIntoView`) and reset zoom to `1` ("a readable zoom level," AC #4) if it isn't already `1`.** `HTMLElement.prototype.scrollIntoView` is not implemented in `jsdom` (a known, accepted limitation elsewhere in this test suite already, e.g. the "Not implemented: navigation to another Document" warnings already tolerated in `apps/web`'s test output) — calling it is a safe no-op in tests; assert the call happened via a spy, not via any resulting scroll position.
- **Gutter markers continue to render for every Beat in `concept.beats`** (matches today's existing behavior — `MOCK_CONCEPT.beats` is a small, fixed, fully-known array; there's no "not yet generated" boundary to hide markers for in this mock, unlike Story 3.3's real-backend `NO_FURTHER_BEATS` case). Clicking a marker ahead of the current position still works exactly as `goToLessonBeat` already allows today (jumping forward past intermediate Beats) — the stacked canvas will render those intermediate Beats fully revealed per the rendering-model bullet above, so there's no visual gap.

## Review Findings

One adversarial review ran against the diff. Two genuine defects found and patched; one claimed defect independently re-verified and found to be a false alarm (documented, not silently dismissed).

### Patched

- **MEDIUM — clicking the gutter marker for the Beat you're already on wiped its in-progress reveal.** `handleGutterMarkerClick` called `goToLessonBeat(index)` unconditionally, and `goToLessonBeat` resets `revealedUnits` to `0` for any Beat not yet in `visitedBeatIds` — which includes the ACTIVE Beat itself while it's still mid-reveal (it only joins `visitedBeatIds` once fully revealed). A learner clicking their own current Beat's marker mid-sentence would see it jarringly restart from scratch. Fixed by skipping the `goToLessonBeat` call when already on that Beat (and not mid-"explain more" detour) — the zoom-reset and scroll-into-view still happen. Covered by a new test using Beat 2 specifically (Beat 1 is pre-seeded into `visitedBeatIds` by the component's own initial state, so it wouldn't have exercised this path) — verified to genuinely catch the regression by temporarily reverting the fix and confirming the test fails, then restoring it.
- **LOW — `handleRestartConcept` didn't reset zoom or scroll position.** A learner who'd zoomed in/out or scrolled deep into the Beat stack before restarting a concept stayed zoomed/scrolled away after restart, even though the stack itself shrank back to just Beat 1. Fixed: resets `zoomLevel` to `1` and calls `canvasRef.current.scrollTo({ top: 0 })` (guarded — `Element.prototype.scrollTo` isn't implemented in `jsdom`, unlike the softer `scrollIntoView` no-op; calling it unguarded crashed the test run). Covered by a new test.

### Investigated and found to be a false alarm (not patched)

- The reviewer claimed gutter-marker positioning (`offsetTop`/`scrollHeight`) computes against the wrong coordinate space because "neither `.usavvy-board-canvas` nor `.usavvy-board-canvas-zoom-wrapper` is positioned." Independently re-verified against the CSSOM View spec (confirmed via MDN): **an element with a CSS `transform` value other than `none` is *also* a qualifying `offsetParent`, not only a positioned ancestor** — and `.usavvy-board-canvas-zoom-wrapper` always has `transform: scale(...)` applied (even at `zoomLevel: 1`, the value is the string `"scale(1)"`, never `"none"`). So the wrapper was already the correct `offsetParent` for each Beat section; the reviewer's diagnosis of the failure mode was incorrect, though the underlying code was implicit/fragile (relying on the transform's side effect rather than stating the intent directly). Made it explicit anyway — added `position: relative` to `.usavvy-board-canvas-zoom-wrapper` — which is a no-op today (the transform already wins as the nearer `offsetParent`) but removes the fragility if a future change ever made the transform conditional on `zoomLevel !== 1`. No test/behavior change; documented here rather than silently corrected without explanation.
