# Story 3.13: Concept-Boundary Checkpoint Questions

Status: done

*(Epic 3, FR-B-24. A real backend story, back on `services/board-orchestration`'s `learningSessions` module (Stories 3.1-3.3's pattern), not a frontend-only story like 3.4/3.11/3.12. Read the CRITICAL SCOPE NOTE before starting any task.)*

## Story

As a learner,
I want short checkpoint questions at the end of a concept,
so that the system can gauge my understanding without it feeling like a graded test.

## Acceptance Criteria

1. **Given** a Concept has reached its final Beat **When** the Concept boundary is reached **Then** between 1 and 3 checkpoint questions related to that Concept's content are presented on the board
2. **Given** I answer a checkpoint question **When** I submit my answer **Then** I receive immediate feedback and the result is recorded as a mastery signal for that concept, presented as feedback rather than a graded score
3. **Given** all checkpoint questions for a Concept are answered **When** the last one is submitted **Then** a domain event carrying the mastery signal is published to the shared event bus per AD-13, for consumption by other modules, and the board proceeds to the next Beat/Concept
4. **Given** I close the session mid-checkpoint **When** I return **Then** the checkpoint resumes at the unanswered question rather than restarting

## CRITICAL SCOPE NOTE — read before starting any task

**Confirmed by researching `epics.md`'s Story 4.14 (the downstream consumer of this story's own event) and re-reading `services/board-orchestration`'s existing `learningSessions` module in full before starting.**

- **This story is the PRODUCER of a checkpoint-result event, not the "mastery" event itself — don't invent a `mastery_score` field.** `epics.md`'s Story 4.14 ("Publish Mastery and Completion Events," `plans-progress`, not `board-orchestration`) explicitly describes itself as consuming *"a checkpoint-result domain event from Story 3.13 (Board) indicating a Concept's checkpoint was passed"* and doing the actual score-band interpretation (`in_progress`/`understood`/`mastered`) itself, in the module that owns `ConceptProgress` (AD-14 — not this one). This story's job is narrower and more honest: publish the RAW per-question results (which question, which option was selected, whether it was correct) — not a computed score. Event name: `"concept.checkpoint_completed"` (past-tense, matching `"learning_session.ended"`'s own convention), payload `{ sessionId, userId, conceptId, results: [...] }`.
- **Checkpoint questions are caller-supplied at session creation, exactly like Beats (Story 3.1's own established pattern) — not generated by this story.** Extend `createOrResumeLearningSession`'s existing signature with an optional `checkpointQuestions` parameter, stored once at creation (ignored on an idempotent-return, same as `beatInputs` already are). No `GenerationPort` binding, no new provider dependency — this mirrors Beats' own precedent exactly.
- **Checkpoint questions/answers are opaque `jsonb` blobs this service stores and returns verbatim, never interprets — the exact same convention already used for `beats.boardAction`/`learningSessions.boardRenderState`.** In particular, this service does **not** grade the answer itself (does not read a caller-supplied `correctIndex` and compare it) — the caller (frontend, eventually) already knows whether the selected option was correct (the mock's own `CheckpointQuestion.correctIndex` proves this data is already available client-side) and reports `{ questionIndex, selectedOptionIndex, isCorrect }` directly. Don't add grading logic this service has no business owning.
- **AC #4's "resumes at the unanswered question" needs no new mechanism of its own — it falls out of `GET /learning-sessions/:id` returning both `checkpointQuestions` and `checkpointAnswers`.** A future caller can compute "the first question index with no matching entry in `checkpointAnswers`" itself; this story does not need to track or return a separate "current checkpoint question index" field.
- **Duplicate-completion-publish guard: apply Stories 3.1-3.3's own repeatedly-learned lesson from the start, not as a follow-up patch.** Compute "was already complete" (every question already answered) BEFORE recording this answer, and only publish `concept.checkpoint_completed` if the checkpoint transitions from incomplete to complete as a RESULT of this specific write — re-submitting an already-answered question (idempotent overwrite, matching this codebase's established "freely re-editable, last-write-wins" convention for similar cases) must never publish the event a second time.
- **This story does NOT rewire `BoardPage.tsx`'s mocked checkpoint UI onto this real endpoint.** Same as every other Epic 3 backend story — the mock stays exactly as signed off; a future story's job. This story's own frontend footprint is limited to a minimal `apps/web/src/modules/board/api.ts` wrapper (matching Stories 3.1-3.3's own precedent), proven via a real-HTTP integration test, not a UI change.
- **CORRECTED DURING CODE REVIEW — this bullet originally, incorrectly, called the concurrent-answer race "low-probability, worst case a double-publish" and said not to build row-locking for it. That assessment was wrong: it's a genuine lost-update (an answer can silently disappear, not just an extra publish), because this write folds a prior READ into the new value, unlike every sibling write in this module which only transitions a scalar `status`. `SELECT ... FOR UPDATE` inside a transaction is used to close it properly — see Review Findings.** (Left here, struck through in spirit rather than deleted, so a future reader sees the reasoning that changed, not just the current answer.)

## Review Findings

One adversarial review ran against the diff. It found the CRITICAL SCOPE NOTE's own risk assessment was wrong about the severity of the accepted race — not a new defect exactly, but a real bug the story had pre-emptively (and incorrectly) waved off as low-severity. Fixed properly rather than re-documenting the understated version.

### Patched

- **HIGH — the "accepted, low-probability race" was actually a genuine lost-update, not merely a double-publish risk.** The story's own CRITICAL SCOPE NOTE (written before implementation) predicted the worst case as "the completion event published twice." The reviewer traced the actual failure mode: `recordCheckpointAnswer` read `checkpointAnswers` outside any lock, merged in the new answer, and wrote the merged array back guarded only by `WHERE status <> "ended"` — a scalar-transition guard that does nothing to protect a jsonb value being folded from a prior read. Two DIFFERENT questions submitted at the exact same instant (both reading the same starting array) would have one silently overwrite the other's write — an answer permanently disappears, not just an extra publish. This differs from every prior write in this module (`pause`/`resume`/`replay`/`stepBeat`), none of which fold a prior read's VALUE into the new write, only its status. Fixed by wrapping the read-merge-write in a transaction with `SELECT ... FOR UPDATE`, serializing concurrent submissions for the same session — the first use of row-locking in this codebase (every prior race fix used the lighter `WHERE status <> "ended"` optimistic pattern, which doesn't apply here). Verified two ways: a new deterministic `Promise.all` concurrency test (two different questions submitted truly concurrently, asserting both survive) fails reliably (`checkpointAnswers` length 1 instead of 2) across 3 repeated runs with the lock removed, and passes reliably across 3 repeated runs with it restored.
