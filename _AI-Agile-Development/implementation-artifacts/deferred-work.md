Capturing more is a compliance/privacy product decision (what to retain, for how long) beyond this story's stated ACs; recommend a follow-up story if legally required for DPDP Act evidentiary purposes.
- `ParentalConsentPage` (this story) and `VerifyEmailPage` (Story 1.1) both auto-fire their action on page load with no explicit "click to confirm" step — weaker evidence of genuine consent, and nominally reachable by aggressive email-link-prescanning services. Changing this is a UX/compliance decision affecting both pages together, not a Story-1.2-only fix.
- Client (`apps/web`) and server (`core`) each maintain a hand-duplicated copy of `calculateAge` with nothing but a code comment enforcing they stay in sync. This is the story's own explicit, deliberate Dev Notes instruction ("keep the two in sync deliberately"), not an oversight — revisit only if a shared-package build step becomes available to both runtimes.
- `calculateAge`/`parseIsoDate` produce `NaN` rather than throwing on a malformed date string, and `NaN < 18` silently evaluates as "not a minor." Unreachable today: the only server entry point is guarded by `z.iso.date()` before this function ever runs, and the only client entry point is a native `<input type="date">` that can't produce a malformed value. Revisit if either function gains a new, less-guarded caller.
- `POST /users/parental-consent`'s `token` field has no maximum length (`z.string().min(1)` only) — identical to every existing token field in `auth/routes.ts` (verify-email, refresh, google). Pre-existing codebase-wide convention, not unique to this diff.
- `/waiting-for-consent` has no session/state guard, unlike `/age-declaration`'s explicit redirect-to-login. The page is fully static (no API call, no user-specific data), so an out-of-context visit has no real consequence beyond a confusing URL.
