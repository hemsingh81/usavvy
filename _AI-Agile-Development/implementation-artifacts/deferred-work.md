## Deferred from: code review of story-2-14 (2026-08-06)

- No cross-service validation that a caller-supplied `courseId` refers to a real, existing, or accessible catalog course — this is the story's own explicit, documented scope decision (see its CRITICAL SCOPE NOTE), matching the established "an opaque cross-service id is trusted, never validated" convention `customCourseId` itself has always followed. A forged/nonexistent `courseId` has no security consequence (every read/delete path is scoped by `ownerId` first, per AC #4), only a wasted, permanently-unretrievable upload — an accepted data-quality gap, not a correctness or privacy one. Revisit only if a future story needs to guarantee every attached note maps to something real (e.g. surfacing "notes attached to this course" back on `CourseDetailPage`).
- No DB-level `CHECK` constraint enforcing the new "exactly one of `customCourseId`/`courseId`" invariant on `uploadedDocuments`/`chunkEmbeddings` — matches this codebase's existing, established convention (no table in this schema uses a `CHECK` constraint for a cross-column invariant; a schema-wide convention change, not story-scoped). The invariant is enforced at the application layer (`resolveUploadGroupKey`, and symmetrically re-verified in `embedAndProposeOutline` before any embedding work starts) with a fail-fast guard for the "both" or "neither" case if a future write path ever bypasses it — a defense-in-depth backstop, not a substitute for a DB constraint. Worth reconsidering as part of any future pass that revisits this codebase's blanket "no CHECK constraints" convention.
- The `pg_advisory_xact_lock` guarding the 10-file cap is keyed only on the grouping key's value (`hashtext(groupKey.value)`), not `ownerId + groupKey.value`. This was harmless when the key was always a self-minted, effectively-owner-unique `customCourseId`; a `courseId` is a shared catalog course id, so two *different* learners attaching notes to the same popular course at the same time now unnecessarily serialize against each other's transactions (a liveness/contention gap, not a correctness bug — the `ownerId` `WHERE` clause on the actual count/insert is unaffected). Low real-world impact (lock duration is a single short transaction); revisit if catalog-course note uploads ever become a high-concurrency hot path.
- No DB index on the new `course_id` column on `uploaded_documents`/`chunk_embeddings`, even though `countExistingFiles`/`listUploadedDocuments` now run `WHERE owner_id = ? AND course_id = ?` against it. Mirrors the identical, pre-existing unindexed-lookup gap `custom_course_id` has always had (not a regression this story introduced) — premature to add ahead of any real query-volume data, matching this codebase's repeated "don't optimize prematurely" precedent (Story 2.12's `proposedTopics`/`proposedConcepts` sequential-insert dismissal is the same class of decision).
- The "exactly one of `customCourseId`/`courseId`" invariant is a genuine discriminated union (`UploadGroupKey`) in exactly one place (`services/ingestion/src/modules/uploads/service.ts`) but left as two independently-nullable fields everywhere else it appears (`VectorStoreEntry`, `uploadedDocumentResponseSchema`, the Drizzle schema itself, and a second, differently-shaped `UploadGroupKey` on the `apps/web` side) — nothing in any of those types alone rules out "both" or "neither" at compile time, which is exactly why `embedAndProposeOutline` needs a runtime guard. Modeling the invariant as a true discriminated union everywhere it's read/written would be a more invasive schema-wide refactor (Drizzle doesn't support a "exactly one of two nullable columns" column-level type); the current single-point-of-truth-plus-runtime-guard approach was judged sufficient for this story's scope.
