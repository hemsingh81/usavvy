## Deferred from: code review of story-1-2 (2026-08-05)

- Parental-consent/verification email bodies are relative URLs (`/parental-consent?token=...`, `/verify-email?token=...`) with no scheme/host — unclickable in a real email client. Matches Story 1.1's identical pattern; `NotificationPort` has no real email provider wired yet (AD-12), so no real email is sent today. Needs a `WEB_APP_URL`-style config decision before either email path is production-ready — recommend addressing before AD-12's real provider is wired in.
- `version` optimistic-concurrency column is bumped unconditionally on every write (`bumpVersion()`) with no compare-and-swap WHERE clause tying it to the version just read — it provides no actual lost-update protection today. This is Story 1.1's own established convention (verifyEmail, googleAuth, refreshSession all do the same); fixing it is a cross-cutting redesign of every user-write path, not scoped to this story.
- No self-service "resend consent email" path — a learner whose 24h token expires, is consumed accidentally, or whose email never arrives is permanently stuck (`AGE_ALREADY_DECLARED` blocks any retry once `birthdate` is set). Same shape as Story 1.1's already-deferred "no resend-verification" gap; needs a new AC/task, not a patch.
- `declareAge`'s minor-path DB writes (user update + token insert) and the parental-consent email send are three separate un-transacted operations — a crash or email-send failure mid-flow leaves the account in a stuck, non-retryable state. Mirrors Story 1.1's signup path (verification email sent the same un-transacted way) — an accepted systemic pattern, not new to this diff.
- Age-boundary "today" is computed via UTC (`toISOString().slice(0,10)`) on both server and client, so a user in IST near midnight can be classified a calendar day off from their real local date. Trusting a client-submitted local date instead would open a worse integrity hole (spoofable birthdate math); revisit only alongside a broader "user timezone" design.
- No DB-level CHECK constraints enforcing new invariants (e.g. `parentConsentedAt` implies `parentEmail` is set, or `parentEmail` being null on an adult row). No existing table in this schema uses CHECK constraints for cross-column invariants — would be a schema-wide convention change, not a story-scoped fix.
- No audit trail beyond a single timestamp (`parentConsentedAt`) for parental consent — no IP address or user-agent captured at the moment of consent. Capturing more is a compliance/privacy product decision (what to retain, for how long) beyond this story's stated ACs; recommend a follow-up story if legally required for DPDP Act evidentiary purposes.
- `ParentalConsentPage` (this story) and `VerifyEmailPage` (Story 1.1) both auto-fire their action on page load with no explicit "click to confirm" step — weaker evidence of genuine consent, and nominally reachable by aggressive email-link-prescanning services. Changing this is a UX/compliance decision affecting both pages together, not a Story-1.2-only fix.
- Client (`apps/web`) and server (`core`) each maintain a hand-duplicated copy of `calculateAge` with nothing but a code comment enforcing they stay in sync. This is the story's own explicit, deliberate Dev Notes instruction ("keep the two in sync deliberately"), not an oversight — revisit only if a shared-package build step becomes available to both runtimes.
- `calculateAge`/`parseIsoDate` produce `NaN` rather than throwing on a malformed date string, and `NaN < 18` silently evaluates as "not a minor." Unreachable today: the only server entry point is guarded by `z.iso.date()` before this function ever runs, and the only client entry point is a native `<input type="date">` that can't produce a malformed value. Revisit if either function gains a new, less-guarded caller.
- `POST /users/parental-consent`'s `token` field has no maximum length (`z.string().min(1)` only) — identical to every existing token field in `auth/routes.ts` (verify-email, refresh, google). Pre-existing codebase-wide convention, not unique to this diff.
- `/waiting-for-consent` has no session/state guard, unlike `/age-declaration`'s explicit redirect-to-login. The page is fully static (no API call, no user-specific data), so an out-of-context visit has no real consequence beyond a confusing URL.
