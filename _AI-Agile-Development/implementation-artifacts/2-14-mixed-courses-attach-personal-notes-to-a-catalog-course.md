# Story 2.14: Mixed courses — attach personal notes to a catalog course

Status: done

*(Epic 2, FR-C-14, the final story of Epic 2. Everything Stories 2.7-2.13 built assumes an upload is building a brand-new "custom course" from scratch — a bare `customCourseId` that either stays private forever or gets promoted into a real `courses` row via Story 2.13's outline-confirm flow. This story introduces the orthogonal case: attaching a personal notes file to a catalog Course that **already exists** (browsed via Story 2.2's catalog, viewed via Story 2.3's `CourseDetailPage`) — no outline review, no promotion, just supplementary private material the Avatar can draw on alongside the official content in some future Epic 3 board session. Read the CRITICAL SCOPE NOTE before starting.)*

## Story

As a learner,
I want to attach my own personal notes to a catalog course,
so that the Avatar can reference both my notes and the official course material during our session.

## Acceptance Criteria

1. **Given** a learner enrolled in a catalog Course **When** they upload a personal notes file (subject to the same format, size, and copyright attestation rules as Story 2.7) **Then** the file is stored as a private UploadedDocument tagged with that Course's ID, and queued through the standard ingestion pipeline (Stories 2.9-2.10)
2. **Given** a personal notes document successfully ingested and embedded against a catalog Course **When** its ContentChunks are written to the vector store **Then** each chunk's metadata includes the catalog courseId alongside its documentId and chunkId, so retrieval during a board session can draw on both catalog material and the learner's notes
3. **Given** a learner's personal notes file fails ingestion (any failure reason from Story 2.11) **When** the failure occurs **Then** the catalog course and its official material are unaffected, and the learner sees the same failure status and reason as for a standalone custom-course upload
4. **Given** personal notes attached to a catalog Course by one learner **When** any other learner accesses that same catalog Course **Then** the notes remain private and are never visible or referenced in that other learner's session

## CRITICAL SCOPE NOTE — read before starting any task

**Confirmed by full-codebase research (grep + full-file reads across `services/ingestion`, `services/gateway`, `packages/shared-types`, `apps/web`). Read every bullet before writing code.**

- **`uploadedDocuments.customCourseId` is `NOT NULL` today, with no `courseId` column anywhere.** (`services/ingestion/src/db/schema.ts:21`.) Every upload path (`uploadDocument`/`pasteText`/`importFromUrl` in `services/ingestion/src/modules/uploads/service.ts`) either uses a caller-supplied `customCourseId` or mints a fresh one via `randomUUID()` (`finalizeUpload`, line 263) — there is **zero existing concept** of attaching an upload to an already-existing catalog `courses.id` instead of a self-contained batching key. This story adds it: make `customCourseId` **nullable**, add a new nullable `courseId: uuid("course_id")` column (same opaque, non-FK convention as every other cross-service id in this schema — AD-14 forbids a real FK). **Exactly one of the two must ever be set** — enforced in the service layer (see Task 1), never as a DB `CHECK` constraint (no table in this schema uses one for a cross-column invariant; would be a schema-wide convention change, not story-scoped).
- **`chunkEmbeddings` has the identical `customCourseId NOT NULL` shape** (`schema.ts:82`) and needs the identical nullable-plus-new-`courseId` treatment, since AC #2 requires the real catalog `courseId` to reach the vector store's metadata. `VectorStoreEntry` (`services/ingestion/src/modules/generation/vectorStorePort.ts`) currently hard-requires `customCourseId: string` — generalize to `customCourseId: string | null` plus a new `courseId: string | null`, mirroring the schema exactly. The pgvector adapter (`vectorStorePgvector.ts`) and mock adapter (`vectorStoreMock.ts`) both just pass whatever `VectorStoreEntry` fields they're given straight through — no adapter-level logic needs to branch on which one is set.
- **Personal notes attached to a catalog Course skip outline proposal entirely — they never reach `"outline ready"`, and there is no outline-review screen for them.** A catalog Course already has its own official Topic/Concept structure (Epic 2's catalog content, Story 2.1); personal notes are supplementary retrievable context for a future board session, not a new outline needing Story 2.13-style review. **AC #2 only mentions the embedding step — it does not mention outline proposal at all.** `embedAndProposeOutline` in `services/ingestion/src/modules/uploads/jobs/ingestDocument.ts` (lines 89-163) must branch: when `document.courseId` is set, embed the chunks and upsert to the vector store exactly as today, then skip the `generationPort.proposeOutline()` call and the `proposedTopics`/`proposedConcepts` inserts entirely, landing on a **new terminal status** (this story adds one — do not reuse `"outline ready"`, whose very name and downstream UI link (`UploadPage.tsx`'s "Review outline" link, `apps/web/src/modules/uploads/ingestionStatus.ts`'s `"Outline ready"` label) are specifically about the outline-review screen this flow never uses). When `document.customCourseId` is set (the existing Story 2.7-2.13 path), behavior is **completely unchanged**.
- **No cross-service validation of `courseId`'s existence, ownership, or the caller having "started" it.** Confirmed via grep: nothing in `services/courses` gates any action on "has this learner called `startCourse` for this course first" — `startCourse`/`learnerCoursePins` only records an idempotent version-pin for later resolution (Story 2.6), never an access gate. `services/gateway`'s only existing cross-service orchestration route (`outlineConfirmationProxy.ts`, Story 2.13) exists because outline-confirm *creates* a real `courses` row and needs `courses` to do that — this story never calls `courses` at all, it only tags a private, `ownerId`-scoped row with an opaque id. Matches this codebase's existing "an opaque cross-service id is trusted, never validated" convention (`customCourseId` itself has never been validated against anything either). **Do not add a `gateway`→`courses` existence check for `courseId` — it would be new, unprecedented complexity solving a problem this story doesn't have** (a wrong/forged `courseId` has no security consequence: results are always scoped by `ownerId` first, matching every other list/delete function in `ingestion`, so AC #4's privacy guarantee holds regardless of whether `courseId` is "real").
- **`services/gateway`'s upload/list/delete routes are dumb 1:1 forwards today** (`ingestionProxy.ts`, confirmed by full read) — `POST /uploads` forwards the raw multipart buffer byte-for-byte, `GET /uploads`/`POST /uploads/paste-text`/`POST /uploads/url-import`/`DELETE /uploads/:id` forward the parsed body/query verbatim with zero inspection of `customCourseId` or any new `courseId` field. **This story needs zero `gateway` code changes** — a new `courseId` multipart field or JSON body field passes through automatically, exactly like `customCourseId` already does.
- **Reuse the exact Story 2.7 constraints, not a rewritten copy.** Same file types (`SUPPORTED_FILE_EXTENSIONS`), same `MAX_FILE_SIZE_BYTES` (50 MB), same `MAX_PAGES` (300), same copyright-attestation-gates-everything ordering, same "10 files" cap semantics — just keyed by `courseId` when that's the grouping key present, exactly as it's keyed by `customCourseId` today (`finalizeUpload`'s `countExistingFiles`/`pg_advisory_xact_lock(hashtext(...))` pattern generalizes directly: lock/count on whichever of `courseId`/`customCourseId` is non-null for this upload).

## Dev Notes

### Architecture constraints that apply directly to this story

- **AD-13/AD-14 (service boundaries, entity ownership):** `courseId` is a bare, opaque, non-FK reference to `services/courses`' `courses.id` — same convention as `courses.ownerId`/`courseCustomizations.userId`/every other cross-service id in this codebase. `ingestion` never calls `courses` to validate it (see CRITICAL SCOPE NOTE).
- **AD-17 (no silent failures):** a both-`customCourseId`-and-`courseId` request is a genuine caller bug (client or a hand-crafted request) — reject it explicitly with a clear `VALIDATION_ERROR`, don't silently pick one and mask the mistake.
- **AD-1 (scaffold-on-demand):** this story deliberately does **not** build outline review, Topic/Concept generation, or any promotion-to-real-course path for catalog-attached notes — none of that is needed for a supplementary-retrieval-context file, and inventing it ahead of any real board-session consumer (Epic 3, still backlog) would be exactly the kind of fabricated-capability Stories 2.9-2.13 have consistently refused to build ahead of need.

- **Story 2.13 (`2-13-review-and-edit-the-proposed-outline.md`) is the most structurally similar previous story** — also touched `uploadedDocuments`/`chunkEmbeddings`-adjacent schema, also needed a migration reviewed carefully after a design flaw was caught mid-review (the `customCourseConfirmations.courseId` nullable redesign, documented in that story's own schema.ts comment). The advisory-lock pattern (`pg_advisory_xact_lock(hashtext(${customCourseId}))`) exists specifically because Story 2.7's own code review found a real two-concurrent-uploads race on the 10-file cap; generalizing the lock key must preserve that exact protection for the new `courseId`-keyed case, not just the happy path.
- **Story 2.7's Dev Notes ("why `customCourseId` is a bare uuid, not yet a real `courses` row")** explicitly frames the ONE direction this codebase has built so far: `customCourseId` → (learner review) → promoted into a real `courses` row (Story 2.13). The new `courseId`-from-route-param mode doesn't have this problem — `courseId` is already known at mount — but the refactor must not accidentally break the `customCourseId` mode's existing "learned from first response" behavior, which several existing passing tests already lock in.

## Review Findings

Three parallel adversarial reviews (Blind Hunter, Edge Case Hunter, Acceptance Auditor) ran against the diff. The Acceptance Auditor independently re-ran the test suites and `drizzle-kit check`/`generate` rather than trusting the Dev Agent Record's own claims, and found no genuine AC or scope-note violations. Findings triaged below; Patch items are applied and covered by tests, Defer items are logged in `deferred-work.md`.

### Patched

- **HIGH — asymmetric invariant guard in `embedAndProposeOutline`.** The "neither `customCourseId` nor `courseId` set" case threw a defensive `INTERNAL_ERROR`, but the mirror-image "both set" case silently took the `courseId` branch, dropping the stray `customCourseId` with no error — and the guard ran *after* `vectorStorePort.upsert` had already persisted a `chunk_embeddings` row, so an invariant violation would have already done partial, hard-to-undo work before ever failing. Restructured: the check is now symmetric (`(customCourseId === null) === (courseId === null)`) and runs up front, before any embedding work starts, failing the document cleanly with `status: "failed", failureReason: "internal error"` and zero `chunk_embeddings` rows written. Covered by two new tests (both-set, neither-set).
- **MEDIUM — malformed `courseId` in the URL silently polls forever.** `UploadPage.tsx`'s `courseId` route param was passed straight into `listUploadsQuerySchema.parse` with no client-side shape check; a bad/stale link's `z.uuid()` failure threw a `ZodError` *before any network call*, which the existing "treat any failure as transient, keep retrying" catch swallowed indefinitely — a permanent failure masquerading as a transient one, retried every 4 seconds forever with zero learner-visible feedback. Fixed by validating the UUID shape up front (mirroring the server's own check) and showing an explicit "this course link looks invalid" message instead of ever entering the fetch/poll loop. Also kept a narrower `ApiError`/`VALIDATION_ERROR` catch in the polling loop itself as defense-in-depth for a legitimate server-side validation failure occurring after the initial fetch succeeded.
- **LOW — a single response-shape drift could have sent both `customCourseId` and `courseId` on a later file in the same batch.** In `courseId` mode, `handleFiles`'s local `activeCustomCourseId` was reassigned from `document.customCourseId` after every upload, relying entirely on the server's documented promise that this is always `null` for a `courseId`-scoped response. Made this structurally impossible instead of promise-dependent: `activeCustomCourseId` is now forced to `undefined` whenever `routeCourseId` is set, regardless of what the server returns.
- **Doc correction** — Task 1's own text claimed `deleteUploadedDocument` needed the same grouping-key generalization as `listUploadedDocuments`; the implementation correctly left it untouched (it's scoped by row `id` + `ownerId`, never a grouping key). Corrected in Task 1 above rather than changing the code.
- Added a courseId-scoped crash-resume test (`ingestDocument.test.ts`, a document parked at `"parsed"`) — the from-scratch tests didn't cover this pipeline's historically bug-prone resume path for the new branch.

### Deferred (see `deferred-work.md`, "Deferred from: code review of story-2-14")

No cross-service validation that `courseId` refers to a real/accessible catalog course (the story's own explicit, already-documented scope decision — re-confirmed, not new); no DB `CHECK` constraint for the exactly-one-of invariant (matches this codebase's no-CHECK-constraints convention; the application-layer guard added in the HIGH patch above is the accepted backstop); the advisory lock's cross-owner contention for a shared `courseId` (a liveness gap, not a correctness bug); no index on the new `course_id` columns (mirrors the pre-existing, unindexed `custom_course_id` gap); the exactly-one-of invariant being a true discriminated union in only one place rather than everywhere it's read/written.
