# Story 2.12: Embedding and AI-proposed Topic/Concept outline

Status: done

*(Epic 2, FR-C-9. The first story to introduce two brand-new architecture-spine ports — `GenerationPort` and `VectorStorePort` — neither of which has any code anywhere in this repo yet. It's also the first story where an `UploadedDocument` can advance past `"parsed"` — Story 2.11 built the full forward-compatible display mapping for `"embedding"`/`"outline ready"` specifically anticipating this story, per its own Dev Notes.)*

## Story

As a learner,
I want the system to embed my content and propose a Topic/Concept outline from it,
so that I have a structured starting point instead of a raw pile of pages.

## Acceptance Criteria

1. **Given** ContentChunks for an UploadedDocument that passed the content safety scan **When** the embedding step runs **Then** each chunk is embedded and written to the vector store with the required metadata contract (documentId, courseId, conceptId placeholder, chunkId)
2. **Given** a document's chunks have been embedded **When** outline proposal runs **Then** a proposed Topic/Concept outline is generated, with every proposed Concept linked to the source page/section range it was derived from
3. **Given** a very short document (e.g. a single page or a few paragraphs) **When** outline proposal runs **Then** a minimal viable outline of at least one Topic and Concept is produced rather than failing, with source links intact
4. **Given** a document flagged as safety-borderline in Story 2.10 **When** outline proposal runs **Then** proposed Concepts derived from flagged chunks are marked so the review step (Story 2.13) can surface them distinctly

- **No real LLM/embedding provider is chosen or funded** (`ARCHITECTURE-SPINE.md` Deferred, line 285: *"Real LLM/TTS/ASR provider selection — not yet chosen... ships behind `GenerationPort`/`VoicePort` with a `mock` adapter as the default until a provider is chosen and funded"*). - **`GenerationPort` and `VectorStorePort` are built locally inside `services/ingestion`, not in `packages/service-kernel`.** `ARCHITECTURE-SPINE.md`'s Structural Seed lists a future `services/generation/` folder "scaffolded when Epic 3/4 starts" — that doesn't exist yet, and `ingestion` (Epic 2) is this port's first real caller (AD-2 names `ingestion` as a `GenerationPort` consumer explicitly). - **The outline-proposal algorithm is a deliberately simple, documented heuristic, not real ML clustering** — matching this epic's established "cheap heuristic, not a production classifier" discipline (Story 2.9's font-size heading heuristic, Story 2.10's keyword-scan policy categories). The actual code therefore branches on a new `CHUNKS_ALREADY_COMMITTED_STATUSES = new Set(["parsed", "embedding"])`: those two statuses load the document's *existing* `ContentChunk` rows from the DB and go straight to the shared `embedAndProposeOutline` continuation; every other non-terminal status (`"queued"`/`"parsing"`/`"safety scan"`) still runs the full parse pipeline exactly as before. `vectorStorePort.upsert(...)` is called once, as its own statement (not inside the final transaction) — safe because it's a keyed upsert against deterministic `embed()`/`proposeOutline()` output, so a crash-and-retry between it and the `proposedTopics` transaction just overwrites the same rows with the same values, never duplicating; the `proposedTopics`/`proposedConcepts`/terminal-status write remains one atomic transaction.

## Dev Notes

### Architecture constraints that apply directly to this story

- **AD-1 (ports-and-adapters, scaffold-on-demand):** two brand-new ports (`GenerationPort`, `VectorStorePort`), both mock-first (or mock-only, for `GenerationPort`) — see the Scope Note for the full reasoning on why both live locally inside `services/ingestion/src/modules/generation/` rather than `packages/service-kernel` or a not-yet-scaffolded `services/generation`.
- **AD-2 (GenerationPort owns caching/routing/rate-limiting):** not exercised by this story's `mock` adapter (nothing to cache/route/rate-limit when there's no real model call) — this AD's actual enforcement is `generation/anthropic`'s future job once a real provider exists. Documented as a known gap the mock adapter doesn't need to close, not silently dropped.
- **AD-13/AD-14 (service boundaries, entity ownership):** the entire reason this story stays inside `ingestion`'s own database — see the Scope Note's first two bullets. No cross-service HTTP call, no cross-service DB access, no write into `courses`' owned `Topic`/`Concept` tables.
- **AD-17 (no silent failures):** `"blocked"`/`"failed"` documents are explicitly excluded from the embedding/outline path (Task 4's `if (safetyOutcome.status === "parsed")` guard) rather than silently attempting to embed content that already failed the safety gate.

### Previous story intelligence (Stories 2.9/2.10/2.11 — read before starting, don't rediscover this)

- **`ingestDocument.ts`'s current flow** (post Story 2.11, commit `0ec3f77`): idempotency guard (`TERMINAL_STATUSES` skip) → write `"parsing"` → `storagePort.getObject` → `parseByFileType` → OCR pass → `chunkSections` → write `"safety scan"` → `scanChunks`/`aggregateDocumentOutcome` → one transaction (chunk insert + terminal status: `"parsed"` or `"blocked"`). This story's new work slots in immediately after that transaction commits, conditional on the outcome being `"parsed"`.
- **`aggregateDocumentOutcome` (`contentSafety.ts`) guarantees**: if the document's terminal status is `"parsed"` (not `"blocked"`), every one of its chunks has `safetyStatus` of `"clear"` or `"flagged"` — never `"blocked"` (a single blocked chunk forces the whole document to `"blocked"`, per Story 2.10's `aggregateDocumentOutcome` — `contentSafety.ts:104-109`). This story's embedding/outline step therefore never needs to filter out individual `"blocked"` chunks — that case cannot occur in a `"parsed"` document's chunk set.
- **`chunks[].heading`/`pageRangeStart`/`pageRangeEnd` are already populated** by Story 2.9's chunking/parsing (`heading` from DOCX/MD's real structure or PDF/PPTX's font-size heuristic, `null` for TXT and for DOCX/MD which have no page concept) — Task 1's mock `proposeOutline` reads these fields directly off the same `ContentChunk` shape Story 2.9 already produces, no new upstream data needed.
- **Story 2.11's `TERMINAL_STATUSES` fix (`["parsed", "blocked", "failed"]`)** is the exact mechanism this story's Task 4 extends — Story 2.11's own Dev Notes explicitly anticipated this: *"Story 2.12 (embedding/outline) and Story 2.13 (outline review screen) do not exist yet"* is no longer true as of this story; its forward-compatible `ingestionStatus.ts` display mapping (`apps/web`) needs **zero changes** — confirmed by re-reading that file: `"embedding"`/`"outline ready"` are already fully mapped and tested there with literal hypothetical strings, exactly for this moment.
- **`drizzle-orm@0.45.2`'s native `vector()` column type** (confirmed present at `drizzle-orm/pg-core/columns/vector_extension/vector.d.ts`) removes any need for a new npm dependency or raw-SQL vector handling — a normal Drizzle column + migration, matching every other table in this codebase.

### Why the outline-proposal algorithm groups by heading, not deeper semantic analysis

A `mock` adapter's job is to satisfy the story's ACs deterministically and cheaply, not to approximate real semantic clustering — matching this epic's repeatedly-applied "cheap heuristic now, real capability later behind the same interface" discipline (Story 2.9's heading heuristic, Story 2.10's keyword scan). Heading-grouping is the one structural signal already available on every chunk regardless of source format, and it naturally satisfies AC #2 (each resulting Concept traces to the page/section range of the chunks under that heading) and AC #3 (a document with no headings still produces exactly one fallback group, never zero).
