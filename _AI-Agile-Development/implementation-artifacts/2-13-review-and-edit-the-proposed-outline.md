# Story 2.13: Review and edit the proposed outline

Status: done

*(Epic 2, FR-C-10. The story that finally answers the question every prior custom-course story (2.7-2.12) deliberately deferred: "how does a bare `customCourseId` become a real `courses` row?" It's also the first story in this codebase to (a) give a `courses` row a concept of private, learner-owned data — nothing in `services/courses`' schema/RBAC/access-control layer has ever supported this — and (b) have `gateway` orchestrate two backend services for one client request, rather than a simple 1:1 proxy. Both are genuinely new architecture for this codebase, not just new business logic — read the CRITICAL SCOPE NOTE in full before starting.)*

## Story

As a learner,
I want to review and edit the AI-proposed outline of my uploaded content before I start learning,
so that nothing generated blind becomes part of my course without my approval.

## Acceptance Criteria

1. **Given** a document with a completed proposed outline (Story 2.12) **When** the learner opens the outline review screen **Then** all proposed Topics and Concepts are listed with their source references, and the learner can rename, reorder, merge, delete, or mark any of them as priority
2. **Given** the learner edits the outline (rename/reorder/merge/delete/mark priority) **When** they save their changes **Then** the edited outline replaces the proposed one as the working Topic/Concept structure for that custom course, and no learning session can start against the unreviewed proposal
3. **Given** a learner attempts to delete every proposed Topic in the outline **When** they try to confirm the outline **Then** confirmation is blocked with a message that at least one Topic must remain
4. **Given** a learner merges two proposed Concepts **When** the merge is saved **Then** the resulting Concept retains the union of source page/section references from both original Concepts

## CRITICAL SCOPE NOTE — read before starting any task

**This story spans all three backend services plus `gateway` plus `apps/web`. Read every bullet before writing code.**

- **`courses` has never had a concept of a privately-owned row.** Confirmed by full-schema/RBAC audit: `courses` has no `ownerId` column, `GET /courses/:id` → `getCourse` has **zero access predicate today** (any authenticated user can fetch any course by id, draft or published — a pre-existing, out-of-scope-to-fully-fix gap for catalog content, but NOT acceptable for the genuinely private data this story introduces), and RBAC's only write resource (`courseHierarchy`) is explicitly admin-only content-ops, the wrong shape for "a learner creates their own thing." This story adds a nullable `ownerId text` column to `courses` (same opaque-cross-service-id convention as `courseCustomizations.userId`/`uploadedDocuments.ownerId`) and threads an ownership check into `getCourse`: **if `ownerId` is set, only that owner may fetch it (404 otherwise, matching this codebase's ownership-check-returns-404 convention everywhere else); if `ownerId` is null, behavior is completely unchanged** (existing catalog-content behavior/gap, not this story's job to fix further). Writing a learner's own custom course does **not** go through `requireCourseHierarchyWriteAccess`/RBAC at all — it follows the established "auth-only, service function takes `userId` explicitly, every query scoped by it" pattern (`courseCustomizations`/`learnerCoursePins`'s own precedent), a new dedicated service function, not a new RBAC resource.
- **A custom course's resulting row is `status: "draft"`, never `"published"`.** `searchCourses` (catalog browse, Story 2.2) already filters to `status = 'published'` unconditionally — a `"draft"` owned course already can't leak into catalog search through that filter alone. This story ALSO adds an explicit `ownerId IS NULL` condition to `searchCourses` as defense-in-depth (so even a future bug that flips an owned row to `"published"` still can't leak it into the shared catalog) — belt-and-suspenders, not redundant-for-no-reason.
- **`gateway` has never aggregated two backend services into one client response.** Confirmed: every existing gateway route (`authProxy.ts`, `coursesProxy.ts`, `ingestionProxy.ts`) is a strict 1:1 proxy to exactly one service. `BuildAppDeps` (`app.ts`) already holds both `forwardToCourses` and `forwardToIngestion` in the same object — this story's new "confirm outline" route is the first to use two forwarders in one handler. Build it as a new file (`outlineConfirmationProxy.ts`) with its own two-forwarder `Deps` interface, registered alongside the three existing proxies in `app.ts`. No changes needed to `coreClient.ts`/`coursesClient.ts`/`ingestionClient.ts`/`main.ts` — the closures already exist.
- **No "learning session" exists to actually enforce AC #2's "no learning session can start against the unreviewed proposal."** Session-starting is Epic 3 (backlog) — inventing enforcement for a feature that doesn't exist would be exactly the kind of fabricated capability Stories 2.9-2.12 have consistently refused to build ahead of need. This AC clause is satisfied **structurally, for free**: before confirmation, no `courses` row exists at all for that custom course, so there is nothing for any future Epic 3 code to reference; after confirmation, the real row exists and matches exactly what was confirmed. Document this as the enforcement mechanism, don't build a placeholder guard for a caller that doesn't exist yet.
- **No `Module` level exists in the proposed-outline data (Story 2.12 only ever produced Topics/Concepts).** But `courses`' schema requires every `Topic` to belong to a `Module` (`topics.moduleId` is `NOT NULL`). This story creates exactly **one** default `Module` per confirmed custom course (title: same as the course's own title) and nests every confirmed Topic under it — not a design decision the learner makes or sees, purely a structural necessity to satisfy the existing FK chain. Do not expose "modules" anywhere in the outline-review UI.
- **The custom course needs a title, and nothing upstream of this story has ever collected one.** No AC, no prior story, asks the learner to name their custom course. This story defaults it from the first-uploaded document's `fileName` (stripped of its extension) — documented as a scope decision, not a gap; revisit only if a future story adds an explicit "name your course" step.
- **Merging is scoped to two Concepts within the *same* proposed Topic.** AC #4 doesn't say cross-Topic merge must work, and merging concepts that live under different Topics raises an unscoped question (which Topic does the result belong to?) this story doesn't need to answer. Reject a cross-Topic merge attempt with a clear error, don't silently pick a Topic.
- **Reordering is a bulk "here's the new order" operation, not per-item drag-and-drop.** Matching this codebase's repeated "cheap UI, no new library" discipline (Story 2.11's plain `setInterval` precedent) — the review screen uses up/down move buttons that compute the new position array client-side and PATCH it in one call, not a drag-and-drop library.
- **Idempotent confirmation.** A new `services/ingestion` table (`customCourseConfirmations`) records `customCourseId → courseId` the first time confirmation succeeds. A second confirm call for an already-confirmed `customCourseId` returns the existing `courseId` unchanged rather than creating a second `courses` row — necessary because a network retry of the confirm call must not double-materialize the course. If the cross-service call to `courses` succeeds but the follow-up write to this table fails, the result is an orphaned-but-harmless real `courses` row with no confirmation record — an accepted, documented small window (this codebase already tolerates equivalent cross-service consistency gaps elsewhere, e.g. domain events' own "at least once" framing) — not a transaction spanning two databases, which AD-14 forbids anyway.

## Dev Notes

### Architecture constraints that apply directly to this story

- **AD-13/AD-14 (service boundaries, entity ownership):** `ingestion` and `courses` never call each other directly — `gateway` is the only orchestrator (Task 3). `courses` remains the sole owner of `Topic`/`Concept`; `ingestion`'s `proposedTopics`/`proposedConcepts` are never treated as the same entities, just the provisional data that eventually seeds them.
- **AD-7 (RBAC):** the new `POST /courses/custom` route deliberately does **not** use `courseHierarchy`'s admin-only `can()` gate — see Task 1 and the CRITICAL SCOPE NOTE for why that resource's semantics don't fit a learner's own resource.
- **AD-17 (no silent failures):** a cross-Topic merge attempt is rejected with a real error, not silently resolved to an arbitrary Topic; a zero-Topic confirm attempt is rejected with the specific AC #3 message, not a generic error.

## Review Findings

Three parallel adversarial reviews (Blind Hunter, Edge Case Hunter, Acceptance Auditor) ran against the initial implementation. Findings triaged below; all Patch items are applied and covered by tests, all Defer items are logged in `deferred-work.md`.

### Patched

- **HIGH — ownership check gaps on sibling course-access functions.** `getCourse` had an ownership check, but `getCourseTopicGraph`/`getCourseCustomization`/`saveCourseCustomization`/`getPlacementCheckQuestions`/`scorePlacementCheck`/`startCourse` did not — a real existence oracle plus an actual unauthorized-write vector via `saveCourseCustomization`. Extracted a shared `requireCourseAccessible` helper in `services/courses/service.ts` and threaded `callerUserId`/`userId` through every one of these functions and their `routes.ts` call sites. Covered by new ownership tests in `customization.test.ts`, `placementCheck.test.ts`, `versioning.test.ts`.
- **HIGH — no real idempotency at the point that mattered in outline confirmation.** The original `confirmOutline`/`recordOutlineConfirmation` only recorded idempotency *after* `courses` already created the real row — two concurrent confirms could both observe "not yet confirmed" and both materialize a duplicate `courses` row. Redesigned around an atomic claim-first insert (`customCourseConfirmations.courseId` now nullable; `confirmOutline` claims via `INSERT ... ON CONFLICT DO NOTHING RETURNING *` before any materialization; a losing concurrent caller gets a 409 `OUTLINE_CONFIRMATION_IN_PROGRESS`). New migration `0006_damp_killer_shrike.sql`. Covered by new tests for the claim race (409) and the corrected idempotency test (which now properly claims via `confirmOutline` before calling `recordOutlineConfirmation`, instead of calling the latter directly against a never-claimed row).
- **MEDIUM — `confirmOutline`'s zero-Concepts-per-Topic gap.** AC #3 only says "at least one Topic must remain," but `courses`' own downstream schema (`createCustomCourseTopicInputSchema`) requires every Topic to have ≥1 Concept — a Topic with all its Concepts deleted would pass ingestion's validation, then fail as an opaque 400 from `courses`. `confirmOutline` now checks `topics.some(t => t.concepts.length === 0)` too, rolling back its own claim on rejection so the outline stays confirmable later.
- **MEDIUM — self-merge in `mergeProposedConcepts`.** Merging a concept into itself would update it, then immediately delete that same row — silently destroying it while reporting success. Now rejected with a 400 before either lookup runs.
- **MEDIUM — `reorderProposedTopics`'s duplicate-id gap.** Comparing only `Set` sizes let a duplicate id slip through undetected as long as the `Set` size still matched the current topic count (e.g. current `{A,B}`, request `[A,A,B]`). Added an explicit `orderedTopicIds.length !== currentIds.size` check.
- **MEDIUM — AC #1 violation in `OutlineReviewPage.tsx`.** `sourcePageRangeStart`/`sourcePageRangeEnd` were fetched and typed but never rendered anywhere — AC #1 explicitly requires "all proposed Topics and Concepts are listed with their source references." Now rendered per-Concept.
- **LOW — `OutlineReviewPage.tsx`'s delete buttons didn't treat a 404 as success.** A second click's request landing after the first already succeeded (or any other already-deleted case) surfaced a confusing error instead of just reflecting the already-achieved outcome — matches the established Story 2.11 precedent (`UploadPage.tsx`'s delete button). Fixed for both topic and concept deletes.
- **LOW — `OutlineReviewPage.tsx`'s "at least one Topic" message could co-render with `loadError`.** Unlike the "No proposed outline yet." message (which already checked `!loadError`), the blocking message didn't, so a load failure and the misleading zero-topics message could show simultaneously. Fixed with the same guard.
