# Spine Pair Review — Usavvy

## Overall verdict

The spine pair is well-inherited (sources resolve, FR/NFR IDs and persona names trace verbatim to the PRD, section order matches the canonical DESIGN.md/EXPERIENCE.md shapes exactly) and the frontmatter is internally consistent — every `{path.to.token}` reference resolves. But it is not yet a safe contract for story-dev: the accent color, DESIGN.md's own "primary CTA" and most-clicked interactive color, fails the contrast target the document itself claims to meet; roughly 85% of the components EXPERIENCE.md gives behavioral rules to have no visual spec at all in DESIGN.md (and Radix's "unstyled" posture means there is no fallback to inherit from); and several PRD-flagged, business-critical states (cohort anti-stall, TTS degradation, onboarding resume) have zero UX treatment. These are load-bearing gaps for a downstream dev agent, not polish items.

## 1. Flow coverage — adequate
Checked all 4 Key Flows (J1–J4) for named protagonist, numbered steps, climax beat, failure path.
### Findings
- **high** None of the four Key Flows carries an explicit failure/error branch — every flow is a single happy path ending at its climax beat, unlike the paired example shapes (`experience-example-mobile.md` and `experience-example-shadcn.md`), which append a distinct `Failure:` line to every flow (EXPERIENCE.md:95-129). *Fix:* add a one-line failure branch per flow — e.g. J1: ingestion/outline review declined or Board session fails to start; J2: replan itself rejected/infeasible; J3: cohort dissolves before Meera's session; J4: resubmission still scores low.
- **medium** J4 ("Assignment loop") names no protagonist, unlike J1/J2/J3 (Ananya/Ravi/Meera) — the flow reads as a generic "learner" (EXPERIENCE.md:122-129). This is inherited from PRD §17, where J4 is equally unnamed, so it is a faithful inheritance, but it still fails the mechanical check and is easy to fix without re-eliciting. *Fix:* attach a persona (P1 Ananya fits the self-paced+assignment combination) to give the flow the same concreteness as the other three.
- **medium** J3's climax has Meera "nominated for peer explain-back, accepts" with no branch for declining — the PRD's own OQ-5 explicitly flags peer explain-back as needing careful UX because "unwilling learners must never be put on the spot" and recommends "a clear 'pass' that carries no penalty or visibility" (Doc/00-Requirement.md:455). EXPERIENCE.md never shows the pass path, in the flow or in Component Patterns. *Fix:* add the decline/pass beat to J3 or note it explicitly in Component Patterns.
- **low** J2's "falls behind" step functions as the flow's only quasi-failure moment but is folded directly into the happy path (streak-at-risk nudge → replan) rather than presented as a distinct failure state with its own resolution shape.

## 2. Token completeness — thin
Checked frontmatter token resolution, `{path.to.token}` cross-references, hex presence, and stated contrast targets for load-bearing pairs.
### Findings
- **critical** `colors.accent` (`#EA580C`) with `colors.on-accent` (`#FFFFFF`) computes to ≈3.56:1 contrast — below the 4.5:1 body-text AA target DESIGN.md itself asserts ("All pairings are chosen to clear WCAG 2.1 AA (4.5:1 body text, 3:1 large text/UI) per DC-2," DESIGN.md:170). Accent/on-accent is not a minor pairing: it backs `button-primary` (DESIGN.md:119-123, "reserved exclusively for interaction and reward... primary CTA buttons... 'Explain more' controls") and `star-badge` (DESIGN.md:137-139) — the single highest-frequency interactive surface in the product per Principle 6 ("Explain more must feel free"). `colors.secondary`/`on-secondary` (used on `cohort-seat-pill` filled state) computes to ≈3.75:1, same shortfall. EXPERIENCE.md's Accessibility Floor compounds this by delegating contrast compliance entirely to DESIGN.md ("Color contrast follows `DESIGN.md`'s tokens exactly," EXPERIENCE.md:81) — so the failure propagates downstream with no independent check. *Fix:* darken accent (and/or secondary) or restrict on-accent/on-secondary white text to large-text contexts only; re-verify against the stated 4.5:1/3:1 split per actual type size used.
- **medium** No numeric contrast value is stated or verified for either Board theme's primary text pairing (`board-dark-on-surface` on `board-dark-bg`, `board-light-on-surface` on `board-light-surface`) — DESIGN.md:168-170 asserts a general AA policy but the Board's own narration text (the most continuously-read text in the product, per `board-narration` at 19px, DESIGN.md:84-88) gets no explicit ratio, unlike the indigo-on-teal risk case which is called out by name.
- **low** No `button` (or CTA-label) typography role exists in the `typography` frontmatter block (DESIGN.md:46-96) — button text presumably falls to `label` (13px) or `body-md` (15px), both well under WCAG's 18px/24px "large text" threshold. The absence of an explicit role is part of why the accent contrast failure above is easy to miss: nothing in the spec pins down what size the failing text actually renders at.
- **low** The semantic triad is asymmetric: `error` has `error-container`/`on-error-container`; `warning` and `success` do not (DESIGN.md:21-28). Not necessarily wrong, but undocumented — no prose explains why error alone gets a container variant.

## 3. Component coverage — broken
Checked every component named in DESIGN.md.Components and EXPERIENCE.md.Component Patterns for a matching row in the other file.
### Findings
- **critical** 11 of the 13 rows in EXPERIENCE.md's Component Patterns table have no corresponding visual spec anywhere in DESIGN.md.Components: Source/"Where's this from?", Board Navigation, Checkpoint Interstitial, Skip/Restart Confirmation, Assignment Feedback & Evidence, Certificate Card + Verification Page, Cohort Waiting-List Card, Live Cohort Room Layout, Leaderboard Local-Neighborhood Strip, Transcript Panel, Minor/Parental-Consent Gate (EXPERIENCE.md:47-61 vs. DESIGN.md:194-201). This isn't a cosmetic gap: DESIGN.md's own Foundation choice is Radix UI primitives that are explicitly "unstyled" (EXPERIENCE.md:13), so there is no design-system default to fall back on — a dev building the Assignment Feedback evidence blockquote or the "review recommended" badge (an R-EVAL trust-critical UI, PRD §13.2 FR-E-10) has no color, sizing, or anatomy to build from. *Fix:* add DESIGN.md rows at minimum for the trust-critical set (Source, Assignment Feedback & Evidence, Minor/Parental-Consent Gate) before story-dev; the rest can follow.
- **high** The reverse gap: `Avatar Presence Indicator` and `Star / Streak` have full visual rows in DESIGN.md (DESIGN.md:198-199) but no row in EXPERIENCE.md's Component Patterns table — no behavioral rule for when the Avatar transitions idle→speaking→listening→thinking, what triggers a star's "pop," or how streak-freeze (FR-R-3, 2 freeze days/month) surfaces in the UI.
- **medium** Name mismatch: DESIGN.md names the component `Cohort Seat Pills` (DESIGN.md:200); EXPERIENCE.md never uses that name — it appears only as "a seats-filled pill" folded inside the differently-named `Cohort Waiting-List Card` row (EXPERIENCE.md:57). Rubric criterion 7 (component names identical across sections) fails here specifically.
- **low** `Buttons` (DESIGN.md:196) has no EXPERIENCE.md behavioral row — likely acceptable for a base atom, but every other DESIGN.md component does get one, so the omission is inconsistent with the rest of the pattern.

## 4. State coverage — thin
Walked all 13 IA surfaces (EXPERIENCE.md:25-41) against the 6 State Patterns bullets (EXPERIENCE.md:63-70) and against explicit PRD state/display rules.
### Findings
- **critical** FR-G-6's "anti-stall guarantee" (a waiting list that hasn't formed a cohort within 14 days must offer a smaller cohort, different cadence, or self-paced conversion) has zero state treatment in EXPERIENCE.md. The PRD calls this mitigation "not optional" and rates the underlying risk R-4 "High/**High**" likelihood (Doc/00-Requirement.md:433-437, 679) — it is the single most emphasized state-machine requirement in the whole document and is absent from State Patterns entirely (only the steady-state "not yet estimable" waiting-list card is covered, EXPERIENCE.md:57).
- **high** NFR-6's graceful-degradation state ("if TTS fails, the session continues in text-board mode with a visible notice rather than failing," Doc/00-Requirement.md:541) is not mentioned anywhere in EXPERIENCE.md — a MUST NFR for the Board, the product's core surface, with no corresponding State Pattern.
- **high** Onboarding's resume-at-abandoned-step behavior is an explicit PRD acceptance criterion (AC-A-3.2: "GIVEN a user who abandons onboarding at any step WHEN they return THEN they resume at the abandoned step," Doc/00-Requirement.md:182-186) but is not covered anywhere in EXPERIENCE.md's Foundation, IA, or State Patterns.
- **medium** The forecast algorithm's own explicit display rules (§11.3: "< 5 active days of data → 'Building your pace estimate'"; "velocity = 0 for 7+ days → dormant state; prompt replan, not a forecast"; "Show a range, never a single false-precision date, when confidence is low," Doc/00-Requirement.md:395-399) are not surfaced as states anywhere in EXPERIENCE.md, despite the Progress/Plan surfaces being named in the IA table (EXPERIENCE.md:36).
- **medium** Admin console states are essentially uncovered — State Patterns names only "empty moderation queue" (EXPERIENCE.md:66) as a generic bullet; content QA's draft→review→published→rollback states (FR-O-2), the DMCA/copyright takedown queue (FR-O-4), and the low-confidence-grading review queue (FR-E-10/FR-O-4) get no distinct treatment despite all being MUST admin requirements.
- **low** Catalog/course search has no explicit "no results" state, and upload has no explicit validation-error state for exceeding the stated limits (50MB/300 pages/10 files, FR-C-7) — only post-upload ingestion-stage failures (FR-C-11) are covered.
