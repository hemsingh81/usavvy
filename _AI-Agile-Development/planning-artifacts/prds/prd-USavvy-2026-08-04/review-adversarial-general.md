# Adversarial Review — Usavvy PRD

- §1's own notation legend defines **MUST = "MVP-blocking."** Yet Epic 5 (Cohorts, explicitly Release 3 per §7) and Epic 6 (Assignments, explicitly Release 2 per §7) tag nearly every requirement plain "MUST" with no release qualifier — FR-G-1, FR-G-2, FR-G-4–7, FR-G-9–12, FR-G-16, FR-G-18, and FR-E-1–5, FR-E-7–14 all read as "MVP-blocking" under the document's own definition despite belonging to epics the same document says ship after MVP. Epic 7 and Epic 8 *do* use "(R2)"/"(R3)" suffixes on some items (FR-R-6, FR-R-8, FR-O-3), so the convention exists but is applied inconsistently — a downstream engineer scanning epic tables in isolation (which is exactly how epics/stories get built) has no reliable way to tell MVP scope from later-release scope without cross-referencing §7 prose for every single row.

- §3.2 states Business Objective BO-5 as "**25 catalog courses live at launch**, 100 by month 12," while §7's MVP release plan and OQ-4 both say "**10 seed catalog courses**." These are two different numbers for the same milestone ("at launch") with no reconciling note anywhere in the document.

- OQ-2 ("Primary market and language confirmation... Needed by: Before architecture") is presented as an unresolved stakeholder decision, but §10.6's latency targets and §16.3's compliance scope (NFR-15) are already written as settled numbers/scope explicitly premised on Assumption A1 (India, DPDP Act). The "open" decision has effectively already been answered and load-bearing requirements built on top of it elsewhere in the same draft.

- OQ-3 ("Avatar form: voice-only vs. visual talking head... Needed by: Before spike") is listed as open, but §19.1 makes "a deliberate recommendation" and writes the entire Voice/Generation architecture around voice-only, and the Glossary flatly defines Avatar as "voice plus presence indicator, not a video character (v1)" — stated as settled fact, not as pending. If OQ-3 is genuinely still open, half the architecture section and the glossary are provisional in a way the document never signals.

- OQ-5 ("Peer explain-back: opt-in per session, or cohort-wide? Needed by: Before R3") is listed as open, but FR-G-13 already specifies "rotating, opt-in," the §12.1 BA note already recommends "opt-in-per-session with a clear pass," and FR-R-1 already bakes peer-explain-back into the MUST star-award list. The requirements tables have already answered the question the open-decisions table says is still pending.

- OQ-7 ("Certificate positioning — is any accreditation partnership intended? Needed by: Before R2") is listed as open, but FR-R-5 already mandates the certificate be "explicitly labelled non-accredited" as MUST — again pre-answering the stakeholder question elsewhere in the requirements.

- OQ-6 ("Is human-in-the-loop grading capacity available? Needed by: Before R2") is correctly flagged as blocking, but FR-E-10 (low-confidence gradings queued for human spot-check) and FR-E-11 (appeal → human review queue) are tagged plain MUST for Release 2 with no conditional fallback described. If OQ-6 resolves to "no capacity," these MUST requirements — and the R-EVAL mitigation and the ≥85% agreement-rate success metric that depend on them — are unfulfillable as written, and §7's release plan gives no indication the Release 2 scope would shrink accordingly.

- The mastery-weighted progress formula (§11.2) is internally inconsistent with FR-B-11. Skipped concepts get `mastery_score = 0.0`, but nothing removes their `concept_weight` from the denominator `Σ(concept_weight)` — so a skipped concept counts as weight in the denominator and zero in the numerator, permanently capping the learner's achievable progress % below 100%. This contradicts FR-B-11's claim that skipped concepts are "excluded from mastery" (which reads as excluded from the calculation, not scored as zero-and-counted). No "course complete" threshold is defined anywhere to resolve what % triggers completion/certificate issuance, so this ambiguity directly touches BO-2, FR-P-4, and FR-R-5.

- The `needs_review` state (§11.2, decay "after N days without retrieval") has no assigned `mastery_score` in the formula's enumerated list (only in_progress/understood/mastered/skipped are scored). It is therefore undefined how a decayed concept affects the published progress %. A learner's dashboard number can apparently move without the learner doing anything, with no stated rule — in direct tension with Principle 4 ("Honest progress... reflect demonstrated understanding") which this exact section claims to protect.

- The forecast algorithm (§11.3) divides `remaining` (measured in `concept_weight` units, per §11.2) by `velocity` (measured in raw concepts-mastered-per-day, not weight-per-day). This is a unit mismatch unless every concept has weight 1, which is never stated. As written, `forecast_days = remaining ÷ velocity` is dimensionally inconsistent for any course with non-uniform concept weights, which the weighting scheme in §11.2 implies exists.

- BA recommendation R3 (the mitigation that is supposed to make NFR-B-1/NFR-B-2 latency targets achievable) relies on pre-generating and caching Beats for "catalog courses at the standard depth." But P1's flagship journey (J1, uploaded content) and FR-C-4 (course customisation: overview/standard/deep-dive depth, custom explanation style) both fall outside that cacheable path by construction, and uploaded content is explicitly never shared or cached across learners (NFR-14, privacy). NFR-B-1/B-2 are nonetheless stated as blanket p90 targets with no segmentation by content type or depth — a substantial share of MVP traffic (self-paced uploads, non-standard depth) isn't covered by the mitigation that makes the target plausible.

- NFR-23 requires cost-per-learner-hour to "support ≥60% gross margin at the intended price point," but the price point is exactly OQ-1, an explicitly unresolved open decision. A cost/margin target defined relative to an unknown price cannot be evaluated or tested today, yet it carries an NFR ID and is treated in §16.4's BA note as something the "unit cost model must be built before pricing is set" — creating a circular dependency (cost model needs a price target; price target needs a cost model) that the document doesn't sequence.

- FR-G-6 ("Anti-stall guarantee: if a waiting list hasn't formed a cohort within **X days**...") leaves the threshold as a literal undefined placeholder, even though the accompanying BA note calls this "not optional — it is the mitigation that makes this feature safe to ship" against R-4, which is itself rated High impact / High likelihood. The one number that operationalizes the product's highest-rated cold-start risk mitigation is missing.

- FR-B-6 and FR-B-21 guarantee that repeat-explanation requests use a route/example "not yet used," but the route set is finite (eight listed in FR-B-21) and no fallback behavior is defined for what happens once a learner exhausts all routes and examples for a concept — which is precisely the struggling-learner scenario (via FR-B-12 Restart Concept, or repeated "Explain more") that Principle 2 ("Explain differently, never louder") is meant to serve.

- FR-B-22 (auto-drop difficulty tier and reroute after two failed checkpoints) is tagged SHOULD — explicitly deferrable per the document's own notation — yet it is depicted as expected, reliable behavior in the flagship sample journey J1 ("Avatar auto-drops difficulty and re-routes... concept marked understood"). A deferrable feature is being used to narrate the core value proposition to stakeholders reading the journeys.

- FR-A-8 (data export) is tagged SHOULD, but NFR-15 states the product must be "GDPR-ready (data export, erasure, consent records...)" as a compliance scope item. Treating the actual export mechanism as optional/deferrable while simultaneously asserting GDPR readiness as a requirement is contradictory — GDPR readiness cannot be claimed without the export function it depends on.

- FR-A-2's age gate is self-declared ("age declaration at sign-up") with no verification method specified, and the sequencing between email verification (FR-A-1, "before first session") and parental-consent gating (NFR-16, "before any account activity") is never defined — leaving it ambiguous whether a self-declared minor can complete account/email verification steps before the parental-consent flow triggers. This is a real gap in the exact area (minors, R-8) the document itself flags as a compliance risk requiring careful handling.

- Epic 7's leaderboard-adjacent requirements are inconsistently scoped relative to their own feature. FR-R-6 (Leaderboards) is correctly tagged "MUST (R2)," but FR-R-7 (ranking rules), FR-R-9 (anti-gaming for leaderboards), and FR-R-10 (hide-from-leaderboard control) — all meaningless without leaderboards existing — are tagged plain "MUST" with no release qualifier, implying MVP/R1 scope for logic that only matters once a Release-2 feature ships.

- BO-4 ("≥25% of active learners join at least one cohort") is measured over "the first 12 months post-launch," but cohorts (Epic 5) are explicitly Release 3, sequenced by the document's own BA recommendation R1 to ship *after* R1 and R2 are proven out. Depending on how long R1/R2 take, the effective window to hit a 25% cohort-adoption target could be a small fraction of the stated 12 months, and the document never reconciles the metric's time base with its own recommended release cadence.
